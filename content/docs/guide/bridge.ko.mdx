---
title: '브릿지'
---

`@wvb/bridge`는 웹 앱에서 네이티브 호스트의 Webview Bundle 기능을 호출하는
인터페이스입니다. 설치된 번들을 조회하고, 업데이트 정보를 가져오고, 새 버전을
다운로드하거나 활성화·롤백할 수 있습니다. 파일 시스템과 네트워크 작업은 네이티브
호스트가 수행하며, 브릿지는 Electron, Tauri, Deno Desktop, Android, iOS에서
공통으로 사용할 수 있는 JavaScript API를 제공합니다.

## 브릿지 설정하기

프론트엔드 프로젝트에 패키지를 설치하세요:

<Tabs items={['npm', 'yarn', 'pnpm']}>
  <Tab value="npm">

    ```sh
    npm install @wvb/bridge
    ```

  </Tab>
  <Tab value="yarn">

    ```sh
    yarn add @wvb/bridge
    ```

  </Tab>
  <Tab value="pnpm">

    ```sh
    pnpm add @wvb/bridge
    ```

  </Tab>
</Tabs>

브릿지를 호출하기 전에 네이티브 바인딩을 등록하세요.
[Electron](/docs/guide/electron), [Tauri](/docs/guide/tauri),
[Deno Desktop](/docs/guide/deno-desktop), [Android](/docs/guide/android),
[iOS](/docs/guide/ios) 중 사용하는 플랫폼의 가이드를 참고하세요. 리모트와
업데이터 커맨드를 사용하려면 네이티브 호스트에 해당 기능도 설정해야 합니다.

WebView에서 API를 호출하세요. 예를 들어 활성 버전을 조회할 수 있습니다:

```ts
import { source } from '@wvb/bridge';

const current = await source.getVersion('app');
console.log(current?.version ?? 'Bundle not installed');
```

모든 커맨드는 Promise를 반환하며, 호출이 거부되면 `BridgeError`가 발생합니다.
일부 작업은 전체 호출을 거부하는 대신 번들별 결과를 반환합니다.

## `source`

`@wvb/bridge`에서 `source`를 가져와 로컬 번들 상태를 조회하고 리모트
매니페스트를 관리합니다. 소스는 앱에 포함된 `builtin` 또는 기기에 다운로드한
`remote`입니다.

### `listBundles()`

빌트인과 리모트 매니페스트의 항목을 `SourceListItem[]`로 반환합니다. 각 항목은
`source`와 `item`을 포함하며, `item`에는 `name`, `version`, `status`, `data`가
있습니다. 상태는 `current`, `previous`, `staged`, `orphan` 중 하나입니다.
`data`에는 선택적인 `integrity`와 문자열 값을 갖는 `metadata`가 들어갑니다.

목록에는 제공 중인 버전뿐 아니라 매니페스트에 기록된 다른 버전도 포함됩니다.
번들의 활성 버전을 찾으려면 `getVersion()`을 사용하세요.

### `listBuiltinBundles()`

`listBundles()`와 같은 항목 형식으로 빌트인 번들만 반환합니다.

### `listRemoteBundles()`

`listBundles()`와 같은 항목 형식으로 로컬에 기록된 리모트 번들만 반환합니다.
리모트 서버에 요청하지 않습니다.

### `getVersion(bundleName)`

현재 리모트 버전의 `{ source, version }`을 반환합니다. 리모트 버전이 없으면 현재
빌트인 버전을 사용하며, 둘 다 없으면 `null`을 반환합니다.

### `getRemoteStagedVersion(bundleName)`

스테이징된 리모트 버전 문자열을 반환합니다. 스테이징된 버전이 없으면 `null`을
반환합니다. 스테이징된 버전은 설치를 위해 준비한 상태이며 아직 제공할 버전으로
선택되지 않았습니다.

### `getRemotePreviousVersion(bundleName)`

이전 리모트 버전 문자열을 반환합니다. 기록된 이전 버전이 없으면 `null`을
반환합니다. 업데이터는 롤백할 때 이 버전을 사용합니다.

### `getBuiltinVersionData(bundleName, version)`

지정한 버전에 대해 빌트인 매니페스트의 `{ integrity?, metadata? }`를 반환합니다.
해당 버전의 기록이 없으면 `null`을 반환합니다.

### `getRemoteVersionData(bundleName, version)`

지정한 버전에 대해 리모트 매니페스트의 `{ integrity?, metadata? }`를 반환합니다.
해당 버전의 기록이 없으면 `null`을 반환합니다.

### `updateRemoteVersion(bundleName, version)`

매니페스트에 기록된 리모트 버전을 현재 버전으로 지정합니다.
`{ name, version, kind }`를 반환하며, `kind`는 `settled`, `not_exists`,
`version_not_exists` 중 하나입니다. 아카이브를 다운로드하거나 검증하지 않습니다.
스테이징된 업데이트를 검증하고 활성화하려면 `updater.install()`을 사용하세요.

### `updateRemoteVersions(items)`

여러 번들에 대해 `updateRemoteVersion()`을 수행합니다.
`{ app: '2.0.0', settings: '1.1.0' }`처럼 번들 이름을 버전에 대응시키는 객체를
전달하세요. 요청한 번들마다 결과를 반환하므로 각 결과의 `kind`를 확인하세요.

### `stageRemoteBundle(bundleName, data)`

스테이징할 버전과 선택적인 버전 데이터를 기록합니다. 예를 들어 `data`에
`{ version: '2.0.0', data: { metadata: { release: 'beta' } } }`를 전달할 수
있습니다. `{ name, version, kind }`를 반환하며, `kind`는 `staged` 또는
`in_use`입니다. 현재 사용 중인 버전은 스테이징할 수 없습니다.

이 커맨드는 매니페스트만 변경합니다. 아카이브를 다운로드하거나 파일의 존재
여부를 검증하지 않습니다. 번들을 다운로드하고 스테이징하려면
`updater.download()`를 사용하세요.

### `stageRemoteBundles(items)`

여러 번들에 대해 `stageRemoteBundle()`을 수행합니다.
`{ app: { version: '2.0.0' } }`처럼 번들 이름을 스테이징 데이터에 대응시키는
객체를 전달하세요. 번들별 스테이징 결과를 반환합니다.

### `removeRemoteBundle(bundleName, version, force?)`

리모트 매니페스트에서 버전을 제거하고 해당 아카이브의 삭제를 시도합니다.
`{ name, version, kind }`를 반환하며, `kind`는 `removed`, `not_exists`,
`version_not_exists`, `in_use` 중 하나입니다.

`force`의 기본값은 `false`입니다. 현재 리모트 버전까지 제거하려는 경우에만
`true`로 지정하세요. 빌트인 번들은 제거하지 않습니다.

### `removeRemoteBundles(items)`

여러 버전을 제거합니다. `{ app: { versions: ['1.0.0', '1.1.0'] } }`처럼 번들
이름을 `{ versions, force? }`에 대응시키는 객체를 전달하세요. 요청한 버전마다
결과를 반환합니다. 결과를 확인해 제거되지 않은 버전을 구분하세요.

### `pruneRemoteBundle(bundleName)`

어느 상태에서도 참조하지 않는 `orphan` 버전을 제거하고 아카이브 삭제를
시도합니다. 현재 버전, 이전 버전, 스테이징된 버전은 유지합니다.
`{ name, prunedVersions }`를 반환합니다.

### `pruneRemoteBundles(bundleNames)`

`['app', 'settings']`처럼 이름 배열을 전달하면 각 번들의 `orphan` 버전을
정리합니다. `{ name, prunedVersions }` 결과의 배열을 반환합니다.

### `resolveFilepath(bundleName)`

활성 버전의 네이티브 파일 시스템 경로를 반환합니다. 리모트 버전이 빌트인보다
우선합니다. 활성 버전이 없으면 호출이 거부됩니다. 반환값은 파일 시스템 경로이며,
WebView에서 이동할 URL이 아닙니다.

### `getBuiltinBundleFilepath(bundleName, version)`

지정한 빌트인 번들 버전의 네이티브 아카이브 경로를 반환합니다. 경로를 구하는
작업이므로 해당 위치에 아카이브가 존재하는지는 검증하지 않습니다.

### `getRemoteBundleFilepath(bundleName, version)`

지정한 리모트 번들 버전의 네이티브 아카이브 경로를 반환합니다. 직접 구현하는
다운로드 흐름에서 저장 경로가 필요할 때 사용하세요. 아카이브를 생성하거나 버전을
스테이징하지 않습니다.

### `unload(bundleName)`

네이티브 소스에 캐시된 번들의 디스크립터를 제거합니다. 캐시된 디스크립터를
제거하면 `true`, 그렇지 않으면 `false`를 반환합니다. 아카이브 삭제, 매니페스트
버전 변경, WebView 새로고침은 수행하지 않습니다.

## `remote`

### `getUpdate(options?)`

리모트 업데이트 문서를 가져옵니다. `options.channel`로 릴리스 채널을 선택하고,
`options.etag`로 이전 응답의 ETag를 `If-None-Match` 헤더에 전달할 수 있습니다.
`{ update, etag?, signature? }`를 반환하며, HTTP `204 No Content` 또는
`304 Not Modified` 응답이면 `null`을 반환합니다.

`update`에는 `id`, `createdAt`, `runtimeVersion`, `bundles`, `metadata`가
있습니다. 각 번들은 `name`, `version`과 선택적인 `downloadUrl`, `integrity`,
`metadata`를 포함합니다.

이 커맨드는 로컬에 이미 설치된 버전을 제외하지 않고 서버의 번들 목록을
반환합니다. 예를 들어 다음과 같이 호출합니다:

```ts
import { remote } from '@wvb/bridge';

const response = await remote.getUpdate({ channel: 'beta' });
if (response !== null) {
  console.log(response.update.bundles);
}
```

### `download(url, filepath)`

URL의 내용을 네이티브 파일 시스템 경로에 다운로드합니다. 완료되면 별도의 반환값
없이 Promise가 이행됩니다. 다운로드한 파일을 스테이징하거나 활성화하지 않습니다.
업데이트 문서의 번들을 다운로드하려면 `updater.download()`를 사용하세요.

## `updater`

### `getUpdate(options?)`

활성 로컬 버전과 다른 버전만 `bundles`에 포함한 `Update`를 반환합니다. 적용할
업데이트가 없으면 `null`을 반환합니다. 네이티브 업데이터는 저장된 업데이트와
ETag를 관리하고 런타임 호환성을 검사하며, 네이티브 호스트에 설정된 채널을
사용합니다.

특정 키 ID의 업데이트 서명을 요구하려면 `{ expectSignatureKeyId: 'release' }`를
전달하세요. 네이티브 업데이터에 일치하는 검증 키가 설정되어 있어야 합니다. 이
옵션으로 공개 키 데이터를 전달할 수는 없습니다.

### `download(bundleUpdates, options?)`

전달한 `BundleUpdate[]`를 다운로드하고 스테이징합니다. 옵션은 `concurrency`와
`timeout`입니다. `concurrency`의 기본값은 `3`이며, `timeout`은 밀리초 단위의
업데이터 잠금 대기 시간입니다. 네트워크 요청 제한 시간이 아닙니다.

각 번들의 `name`, `version`, 선택적인 무결성 값과 메타데이터, `result`를 포함한
배열을 반환합니다. 모든 `result.type`을 확인하세요. `downloaded`는 성공을
뜻하며, `error`에는 `code`와 `message`가 포함됩니다. 개별 번들의 실패가 항상
전체 호출을 거부하지는 않습니다. 호출 자체가 실패하면 `BridgeError`가 발생할 수
있습니다.

### `install(targets)`

스테이징된 버전을 검증하고 활성화합니다. 각 대상은 `{ name, version? }`입니다.
`version`을 생략하면 매니페스트에 기록된 스테이징 버전을 사용하고, 지정하면 해당
버전과 정확히 일치해야 합니다.

각 결과에는 `name`, 선택적인 `targetVersion`과 `installVersion`, 다음 중 하나의
`result.type`이 포함됩니다:

| 결과                         | 의미                                                  |
| ---------------------------- | ----------------------------------------------------- |
| `installed`                  | 스테이징된 버전을 활성화했습니다.                     |
| `staged_version_not_matched` | 요청한 버전이 스테이징된 버전과 다릅니다.             |
| `staged_bundle_not_exists`   | 설치할 스테이징 번들이 없습니다.                      |
| `verify_failed`              | 스테이징된 번들이 검증에 실패했습니다.                |
| `error`                      | 작업에 실패했습니다. `code`와 `message`를 확인하세요. |

다운로드에 성공한 버전만 설치하고, 설치 결과를 확인한 뒤 새로고침하세요. 예를
들어 다음과 같이 처리할 수 있습니다:

```ts
import { updater } from '@wvb/bridge';

const update = await updater.getUpdate();
if (update !== null) {
  const downloads = await updater.download(update.bundles);
  const targets = downloads
    .filter(item => item.result.type === 'downloaded')
    .map(({ name, version }) => ({ name, version }));

  const installed = await updater.install(targets);
  const complete = installed.every(item => item.result.type === 'installed');

  if (complete) {
    window.location.reload();
  } else {
    console.error('Update incomplete', { downloads, installed });
  }
}
```

### `rollback(targets)`

각 번들의 이전 리모트 버전을 복원합니다. 각 대상은 `{ name, version? }`이며,
버전을 지정하면 기록된 이전 버전과 일치해야 합니다. `name`, 선택적인
`targetVersion`과 `rollbackVersion`, 다음 중 하나의 `result.type`을 반환합니다:

| 결과                           | 의미                                                  |
| ------------------------------ | ----------------------------------------------------- |
| `rolled_back`                  | 이전 버전을 복원했습니다.                             |
| `previous_version_not_matched` | 요청한 버전이 이전 버전과 다릅니다.                   |
| `previous_bundle_not_exists`   | 복원할 이전 리모트 번들이 없습니다.                   |
| `verify_failed`                | 이전 번들이 검증에 실패했습니다.                      |
| `error`                        | 작업에 실패했습니다. `code`와 `message`를 확인하세요. |

예를 들어 `await updater.rollback([{ name: 'app' }])`은 기록된 이전 버전으로
복원을 시도합니다. 리모트 버전을 처음 설치한 경우에는 이전 리모트 버전이 없을 수
있습니다. 롤백이 자동으로 빌트인 번들을 복원하지는 않습니다.

## 기타 API

### `platform`

페이지에 노출된 네이티브 브릿지를 감지합니다. `platform.type`은 `electron`,
`tauri`, `deno`, `android`, `ios` 중 하나이며, 지원하는 호스트를 감지하지 못하면
`undefined`입니다. boolean getter로 `isElectron`, `isTauri`, `isDeno`,
`isAndroid`, `isIos`를 제공합니다.

플랫폼에 따라 UI를 다르게 표시할 때 사용하세요. 플랫폼 감지만으로 호스트의
리모트나 업데이터가 초기화되었는지 확인할 수는 없습니다. 바인딩이 없는 일반
브라우저에서는 테스트 모킹을 설정하지 않는 한 네이티브 커맨드를 실행할 수
없습니다.

### `invoke(name, params?)`

네이티브 커맨드를 직접 호출하고 `Promise<T>`를 반환합니다. 기본 제공 커맨드는
타입이 지정된 `source`, `remote`, `updater` 메서드를 사용하세요. 예를 들어
`source.getVersion('app')`을 저수준 API로 호출하면 다음과 같습니다:

```ts
import { invoke, type BundleSourceVersion } from '@wvb/bridge';

const current = await invoke<BundleSourceVersion | null>('sourceGetVersion', {
  bundleName: 'app',
});
```

타입 매개변수는 예상 결과를 나타내며, 런타임에 네이티브 응답을 검증하지
않습니다. 네이티브 호스트가 지원하는 커맨드 이름을 사용해야 합니다.

### `BridgeError`

거부된 브릿지 호출에 사용하는 오류 클래스입니다. `message`와 선택적인 `code`로
실패를 처리하세요. `BridgeError.of(code, message?)`는 코드가 있는 오류를
생성합니다. `BridgeError.from(value)`는 알 수 없는 오류 값을 정규화하며, 이미
`BridgeError`이면 해당 인스턴스를 그대로 반환합니다.

### `isBridgeError(value)`

거부된 호출의 오류를 `BridgeError`로 처리할 때 사용하는 타입 가드입니다. 예를
들어 다음과 같이 처리합니다:

```ts
import { isBridgeError, source } from '@wvb/bridge';

try {
  await source.getVersion('app');
} catch (error) {
  if (isBridgeError(error)) {
    console.error(error.code, error.message);
  } else {
    throw error;
  }
}
```

### `isBridgeErrorData(value)`

직렬화된 `{ message: string, code?: string }` 오류 형식인지 검사합니다. 오류
인스턴스 대신 원시 오류 데이터를 다룰 때 사용하세요. 내보내는 타입은
[브릿지 API 레퍼런스](/docs/references/api/bridge)를 참고하세요.

## `@wvb/bridge/testing`으로 테스트하기

네이티브 호스트를 실행하지 않고 프론트엔드 동작을 테스트할 때
사용하세요.

### `mockInvoke()`로 커맨드 모킹하기

`source.getVersion`처럼 공개 메서드 이름으로 핸들러를 등록하세요. 핸들러는 해당
메서드의 인자를 같은 순서로 받으며, 결과를 동기 또는 비동기로 반환할 수
있습니다. TypeScript는 브릿지 API를 기준으로 인자와 반환값의 타입을 검사합니다.

예를 들어 Vitest에서 다음과 같이 사용가능합니다:

```ts title="bridge.test.ts"
import { BridgeError, source } from '@wvb/bridge';
import { clearInvokeMocks, mockInvoke } from '@wvb/bridge/testing';
import { afterEach, expect, test } from 'vitest';

afterEach(clearInvokeMocks);

test('reads the active version', async () => {
  mockInvoke('source.getVersion', bundleName => {
    expect(bundleName).toBe('app');
    return { source: 'remote', version: '2.0.0' };
  });

  await expect(source.getVersion('app')).resolves.toEqual({
    source: 'remote',
    version: '2.0.0',
  });
});

test('preserves a native error code', async () => {
  mockInvoke('source.getVersion', () => {
    throw BridgeError.of('test_failure', 'Simulated native failure');
  });

  await expect(source.getVersion('app')).rejects.toMatchObject({
    name: 'BridgeError',
    code: 'test_failure',
  });
});
```

### `mockBridge()`로 모킹 묶기

커맨드 모킹을 하나의 그룹으로 만들고, 필요하면 플랫폼도 지정하세요.
`mockInvoke()` 호출을 이어 붙이거나 반환된 객체에서 메서드를 호출해 핸들러를
등록할 수 있습니다. `using`을 사용하면 스코프를 벗어날 때 자동으로 정리합니다:

```ts title="platform.test.ts"
import { platform, source } from '@wvb/bridge';
import { mockBridge } from '@wvb/bridge/testing';
import { expect, test } from 'vitest';

test('shows the iOS bundle version', async () => {
  using bridge = mockBridge({ platform: 'ios' });
  bridge.mockInvoke('source.getVersion', () => ({
    source: 'builtin',
    version: '1.0.0',
  }));

  expect(platform.isIos).toBe(true);
  await expect(source.getVersion('app')).resolves.toEqual({
    source: 'builtin',
    version: '1.0.0',
  });
});
```

### `mockPlatform()`으로 플랫폼 지정하기

`mockPlatform('android')`는 커맨드 핸들러를 등록하지 않고 플랫폼 감지 결과만
변경합니다. 반환값은 `Disposable`입니다. `using`을 사용하거나 반환값의
`[Symbol.dispose]()`를 호출해 이전 플랫폼으로 복원하세요.

### `clearInvokeMocks()`로 정리하기

모든 커맨드 핸들러를 제거합니다. 개별 `mockInvoke()`도 정리할 수 있는 핸들을
반환하며, 핸들의 `.clear()`로 해당 핸들러만 제거할 수 있습니다. 두 메서드 모두
플랫폼 설정을 복원하거나 설치된 호출 가로채기 함수를 제거하지는 않습니다.
플랫폼을 모킹했다면 별도로 해제하세요.
