웹뷰 번들 클라이언트와 호환되는 리모트 서버를 구현하는 개발자를 위한 사양입니다.
프로토콜 버전 `1`의 업데이트 조회, 응답 문서, 서명, 다운로드를 정의합니다.
업로드 자격 증명과 제공자 관리 API는 이 규약의 범위에 포함하지 않습니다.

## 적합성

**MUST(필수)**는 호환성 요구사항, **SHOULD(권장)**는 권장 구현 동작,
**MAY(선택)**는 선택적 기능을 나타냅니다. 문서 구조는
[Expo Updates v1](https://docs.expo.dev/technical-specs/expo-updates-1/)의
클라이언트·요청·응답 구성을 참고했습니다. 웹뷰 번들은 자체 헤더와 문서 포맷을
사용합니다.

## 클라이언트 흐름

1. 지원하는 프로토콜·런타임 버전과 선택적인 채널을 지정해 `GET /update`를
   요청합니다.
2. `200` 응답을 받으면 JSON 파싱 전에 요청한 서명을 응답 바이트로 검증합니다.
3. 문서의 번들 목록을 소스의 활성 버전과 비교합니다.
4. 필요한 번들을 다운로드하고 문서에 포함된 무결성 해시를 검증합니다.
5. 다운로드한 파일을 설치 대기 상태로 저장한 뒤, 앱이 정한 시점에 설치합니다.

업데이트 문서는 여러 번들을 나타낼 수 있습니다. 설치 결과는 번들별로 반환합니다.
하나의 문서를 배포해도 클라이언트 설치 전체가 하나의 트랜잭션이 되지는 않습니다.

## 업데이트 요청

클라이언트는 설정한 기본 URL을 기준으로 `GET /update`를 요청해야 합니다(MUST).
요청 헤더는 다음과 같습니다:

| 헤더                          | 필수 여부         | 값                                                     |
| ----------------------------- | ----------------- | ------------------------------------------------------ |
| `wvb-update-protocol-version` | 필수              | `1`                                                    |
| `wvb-runtime-version`         | 필수              | 양의 정수. 클라이언트 런타임 값은 `1`입니다.           |
| `accept`                      | 클라이언트가 전송 | `application/json`                                     |
| `wvb-update-channel`          | 선택              | `stable` 같은 채널 이름. 생략하면 기본 채널입니다.     |
| `if-none-match`               | 선택              | 이전에 수락한 업데이트의 ETag                          |
| `wvb-expect-signature`        | 선택              | 문자열 멤버 `key_id`, `alg`를 포함한 구조화된 딕셔너리 |

런타임 버전은 라이브러리가 관리하며 npm·SDK·앱·번들 버전과는 별개입니다. 채널은
`channel` 쿼리 매개변수가 아닌 헤더로 전달합니다.

`stable` 채널에서 서명을 요구하지 않는 요청 예제는 다음과 같습니다:

```http
GET /update HTTP/1.1
Host: updates.example.com
Accept: application/json
wvb-update-protocol-version: 1
wvb-runtime-version: 1
wvb-update-channel: stable
```

## 업데이트 응답

서버는 요청한 런타임과 채널에 맞는 업데이트를 선택합니다. 다음 상태 코드 의미를
따라야 합니다(MUST):

| 상태 코드 | 의미                                                        | 본문                       |
| --------- | ----------------------------------------------------------- | -------------------------- |
| `200`     | 업데이트 문서가 있음                                        | 업데이트 JSON              |
| `204`     | 제공할 업데이트가 없음                                      | 비어 있음                  |
| `304`     | 선택한 문서가 `If-None-Match`와 일치함                      | 비어 있음                  |
| `400`     | 프로토콜·런타임·서명 요청이 잘못되었거나 요구한 서명이 없음 | 오류 JSON                  |
| `404`     | 요청한 다운로드나 경로가 없음                               | 제공자별 오류 또는 빈 본문 |
| `500`     | 서버 오류                                                   | 오류 JSON                  |

`200` 응답은 `Content-Type: application/json`을 포함해야 합니다(MUST). 조건부
요청을 위해 ETag를 포함하는 것을 권장합니다(SHOULD). `Remote.getUpdate()`는
`204`와 `304` 모두 문서 없이 반환합니다. 업데이터는 `304`에서 이전에 수락한 캐시
문서를 재사용할 수 있지만, `204`를 캐시 업데이트의 사용 허가로 처리하지
않습니다.

본문은 제공자의 저장용 래퍼를 제외한 업데이트 데이터입니다. 최소 예제는 다음과
같습니다:

```json
{
  "id": "0199ba38-8ba0-7000-8000-000000000001",
  "createdAt": "2026-10-17T00:00:00Z",
  "runtimeVersion": 1,
  "bundles": [{ "name": "app", "version": "1.1.0" }]
}
```

문서 필드는 다음과 같습니다:

| 필드             | 타입   | 필수 여부 | 의미                                              |
| ---------------- | ------ | --------- | ------------------------------------------------- |
| `id`             | 문자열 | 필수      | 고유 업데이트 식별자. 제공자는 UUID를 생성합니다. |
| `createdAt`      | 문자열 | 필수      | ISO 8601 생성 시각                                |
| `runtimeVersion` | 정수   | 필수      | 호환되는 라이브러리 런타임 버전                   |
| `bundles`        | 배열   | 필수      | 배포에서 선택한 번들 버전 목록                    |
| `metadata`       | 객체   | 선택      | 키와 값이 문자열인 메타데이터                     |

각 번들 항목은 다음 필드를 포함합니다:

| 필드          | 타입   | 필수 여부 | 의미                                                                      |
| ------------- | ------ | --------- | ------------------------------------------------------------------------- |
| `name`        | 문자열 | 필수      | 번들 이름                                                                 |
| `version`     | 문자열 | 필수      | 버전 식별자. 클라이언트는 유의적 버전 순서가 아닌 동일 여부를 비교합니다. |
| `integrity`   | 문자열 | 선택      | `sha256:BASE64_DIGEST` 형태의 파일 해시                                   |
| `downloadUrl` | 문자열 | 선택      | 코어 클라이언트가 지원하는 사용자 정의 절대 다운로드 URL                  |
| `metadata`    | 객체   | 선택      | 키와 값이 문자열인 메타데이터                                             |

`BASE64_DIGEST`는 `.wvb` 파일 전체의 해시를 Base64로 인코딩한 값입니다. 기본
제공자는 기본 다운로드 경로를 사용하며, 공통 저장 스키마에 `downloadUrl`을
보존하지 않습니다. 해당 필드가 필요하면 사용자 정의 서버를 사용하세요.

## 조건부 요청과 캐시

서버는 `If-None-Match`를 평가하기 전에 런타임과 채널에 맞는 업데이트를 선택해야
합니다(MUST). ETag가 일치하면 `304`를 반환합니다. 공통 서버는 약한 ETag, 쉼표로
구분한 여러 태그, 기존 업데이트에 대한 `*`를 지원합니다.

런타임·채널·서명 요청에 따라 캐시를 분리하세요. CDN이 해당 헤더를 전달하고
오래된 `/update` 응답을 제공하지 않도록 설정하세요. 번들 버전 URL은 불변으로
유지하는 것을 권장합니다(SHOULD). 제공자는 업데이트 문서를 먼저 저장하고 그다음
현재 업데이트 포인터를 변경합니다.

## 서명

클라이언트가 서명을 요구할 때 다음과 같은 구조화된 딕셔너리를 전송합니다:

```http
wvb-expect-signature: key_id="release", alg="ed25519"
```

서버는 해당 키 ID와 알고리즘을 선택하고 다음 헤더를 반환합니다:

```http
wvb-signature: key_id="release", alg="ed25519", sig="BASE64_SIGNATURE"
```

`BASE64_SIGNATURE`는 서명을 Base64로 인코딩한 값으로 바꾸세요. 서명은 응답
본문의 정확한 UTF-8 바이트를 대상으로 해야 합니다(MUST). 클라이언트는 파싱 전에
바이트를 검증합니다. 키 순서를 바꾸거나 공백을 추가하거나 다시 직렬화하면 서명이
맞지 않을 수 있습니다. 신뢰할 공개 키는 앱에 별도로 설정합니다.

공통 서버는 세 가지 정책을 제공합니다:

- `optional`(기본값): 클라이언트가 요청하면 일치하는 서명을 요구합니다.
- `strict`: 제공할 업데이트에 일치하는 서명을 요구합니다.
- `off`: 서명이 없다는 이유로 업데이트를 거부하지 않습니다.

`204` 응답은 본문이 없으며 서명 검증을 거치지 않습니다. 제공할 업데이트가 있으면
ETag 비교보다 서명 선택을 먼저 수행합니다.

<Callout type="warn" title="제공자의 서명 제한">
  0.3.0 제공자는 JSON 객체의 키를 정렬해 서명하지만, 공통 HTTP 핸들러는 저장된
  객체를 별도로 직렬화합니다. 두 바이트열이 달라질 수 있습니다. 서명 서버를 직접
  구현한다면 서명에 사용한 직렬화 결과를 그대로 응답하세요. 서명을 요구하는
  클라이언트를 연결하기 전에 이 동작을 검증해야 합니다. `wvb deploy` CLI도
  설정한 서명을 디플로이어에 전달하지 않으므로, 서명 배포에는 프로그래밍 방식의
  배포 API가 필요합니다.
</Callout>

## 번들 다운로드

`downloadUrl`이 없으면 클라이언트는 `GET /bundles/NAME/VERSION`을 요청합니다.
`NAME`과 `VERSION`은 업데이트 문서의 식별자로 바꾸세요. 저장 파일과 달리 URL에는
`.wvb` 확장자를 붙이지 않습니다.

서버는 번들의 바이트를 그대로 반환해야 합니다(MUST).
`Content-Type: application/webview-bundle`을 사용하고, 크기를 알면
`Content-Length`를 포함하세요. 번들이 없으면 `404`를 반환합니다.
이름·버전·무결성은 다운로드 전용 메타데이터 헤더가 아닌 업데이트 문서에서
읽습니다.

요청 예제는 다음과 같습니다:

```http
GET /bundles/app/1.1.0 HTTP/1.1
Host: updates.example.com
```

## 오류와 검증

공통 서버의 오류 응답은 `message` 필드를 가진 JSON 객체를 사용합니다:

```json
{ "message": "Unsupported update protocol version: 2" }
```

사용자 정의 서버를 연결하기 전에 다음 항목을 검증하세요:

1. 업데이트가 없는 채널의 정상 요청이 본문 없이 `204`를 반환하는지 확인하세요.
2. 배포 후 `200` 응답에 게시한 런타임과 번들이 포함되는지 확인하세요.
3. ETag를 포함해 다시 요청하면 `304`를 반환하는지 확인하세요.
4. 호환되지 않는 프로토콜이나 잘못된 런타임이 `400`을 반환하는지 확인하세요.
5. 다운로드한 파일과 문서의 무결성 해시가 일치하는지 확인하세요.
6. 받은 바이트 그대로 서명을 검증하고, 한 바이트를 바꾸면 검증에 실패하는지
   확인하세요.

구현 근거는
[서버 요청 처리](https://github.com/webview-bundle/webview-bundle/blob/main/packages/remote/base/src/server/factory.ts)와
[Rust 클라이언트](https://github.com/webview-bundle/webview-bundle/blob/main/packages/core/src/remote/remote.rs)를
참고하세요. 제공자를 사용하는 구성은 [제공자](/docs/guide/remote/provider)를
참고하세요.
